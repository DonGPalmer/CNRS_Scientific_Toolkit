# CNRS Scientific Toolkit v0.18.0 exact-addition-and-subtraction API contract

**Status:** DRAFT — PREPARED FOR AUTHOR REVIEW; NOT YET ADOPTED

**Prepared:** 22 September 2026

This contract is subordinate to `V018_ARCHITECTURE_FREEZE.md`. It freezes the
public behavior of exact finite CNRS-A addition, negation, and subtraction for
the accepted grammar. It authorizes no implementation or mutation.

## 1. Public APIs

The following signatures and import paths remain unchanged:

```python
from cnrs.cnrs_add import add_cnrs
from cnrs.cnrs_ops import cnrs_add, cnrs_neg, cnrs_sub

def add_cnrs(a: str, b: str) -> str: ...
def cnrs_add(a: str, b: str) -> str: ...
def cnrs_neg(a: str) -> str: ...
def cnrs_sub(a: str, b: str) -> str: ...
```

They remain re-exported from `cnrs` and from the existing core façade. No
`*_exact` alias, new result class, status enum, witness class, schema, or
algorithm identifier is introduced.

`cnrs_add(a, b)` remains observationally identical to `add_cnrs(a, b)`.

## 2. Accepted exact domain

Each claimed operand is an exact `str` matching:

```text
( [0-4]+ ( "." [0-4]* )? ) | ( "." [0-4]+ )
```

Accepted examples include:

```text
"0"  "1"  "10"  "001"  "1."  ".1"  "0.010"  "23.1"
```

The value of a spelling `d_m...d_0.d_-1...d_-n` is

```text
sum(d_k * beta^k),  beta = -2 + i.
```

The result is always a canonical finite CNRS-A string: no redundant leading
integer zeros, no redundant trailing fractional zeros, at least one integer
digit, and no radix point when the fractional part is empty.

## 3. Normative addition behavior

For accepted operands `a` and `b`:

```python
value(add_cnrs(a, b)) == value(a) + value(b)
add_cnrs(a, b) == cnrs_add(a, b)
```

The implementation must use the frozen 14-state addition relation generated by
exact integer-pair arithmetic. Operand alignment, carry order, output digits,
radix placement, and canonical formatting remain compatible with v0.17.

### 3.1 Fixed addition vectors

| `a` | `b` | Required result |
|---|---|---|
| `"0"` | `"0"` | `"0"` |
| `"1"` | `"2"` | `"3"` |
| `"4"` | `"4"` | `"1313"` |
| `"10"` | `"1"` | `"11"` |
| `".1"` | `".1"` | `"0.2"` |
| `"1"` | `".1"` | `"1.1"` |
| `"23.1"` | `"4.3"` | `"1332.4"` |
| `"0001"` | `"1."` | `"2"` |
| `".4"` | `"4."` | `"4.4"` |

Each vector is commutative: reversing the operands produces the same required
result.

## 4. Normative negation behavior

For every accepted operand `a`:

```python
cnrs_neg(a) == mul_cnrs("144", a)
value(cnrs_neg(a)) == -value(a)
cnrs_neg(cnrs_neg(a)) == canonical(a)
```

`"144"` remains the canonical representation of `-1`.

### 4.1 Fixed negation vectors

| Input | Required result |
|---|---|
| `"0"` | `"0"` |
| `"1"` | `"144"` |
| `"2"` | `"143"` |
| `"4"` | `"141"` |
| `"10"` | `"1440"` |
| `".1"` | `"14.4"` |
| `".4"` | `"14.1"` |
| `"23.1"` | `"1441.4"` |

The nonintegral vectors replace incorrect v0.17 value-map results and are part
of the explicit correction ledger.

## 5. Normative subtraction behavior

For accepted operands `a` and `b`:

```python
cnrs_sub(a, b) == add_cnrs(a, cnrs_neg(b))
value(cnrs_sub(a, b)) == value(a) - value(b)
```

### 5.1 Fixed subtraction vectors

| `a` | `b` | Required result |
|---|---|---|
| `"0"` | `"0"` | `"0"` |
| `"1"` | `"2"` | `"144"` |
| `"4"` | `"4"` | `"0"` |
| `"10"` | `"1"` | `"13204"` |
| `"1"` | `".1"` | `"1320.4"` |
| `".1"` | `".1"` | `"0"` |
| `"23.1"` | `"4.3"` | `"33.3"` |
| `"0001"` | `"1."` | `"0"` |
| `".4"` | `"4."` | `"141.4"` |

## 6. Canonical-equivalence laws

If `a1` and `a2` are accepted spellings with equal exact values, and likewise
for `b1` and `b2`, then:

```python
add_cnrs(a1, b1) == add_cnrs(a2, b2)
cnrs_add(a1, b1) == cnrs_add(a2, b2)
cnrs_neg(a1) == cnrs_neg(a2)
cnrs_sub(a1, b1) == cnrs_sub(a2, b2)
```

Required spelling examples include:

```text
"1" == "1." == "01" == "001.000"
".1" == "0.1" == "00.100"
"0" == "00" == "0." == ".0"
```

## 7. Algebraic laws in the accepted domain

Where all displayed intermediate results are finite CNRS-A strings, the
following must hold by exact value and canonical output:

```python
add_cnrs(a, b) == add_cnrs(b, a)
add_cnrs(add_cnrs(a, b), c) == add_cnrs(a, add_cnrs(b, c))
add_cnrs(a, "0") == canonical(a)
add_cnrs(a, cnrs_neg(a)) == "0"
cnrs_neg(cnrs_neg(a)) == canonical(a)
cnrs_sub(a, a) == "0"
cnrs_sub(a, "0") == canonical(a)
cnrs_sub(a, b) == cnrs_neg(cnrs_sub(b, a))
mul_cnrs(a, add_cnrs(b, c)) == add_cnrs(mul_cnrs(a, b), mul_cnrs(a, c))
```

The independent oracle, not a production operation, is the authority for exact
value comparison.

## 8. Public constants and transition behavior

`CARRY_SET_PAIRS` retains its 14 ordered pairs. `CARRY_SET` remains value- and
container-compatible with the v0.17 module object. `ADDITION_TABLE` remains a
dictionary with 350 entries mapping three-integer keys to two-integer values.

The exact transition-table checksum and serialization are defined by the
architecture freeze. All carry states must drain under repeated `(0,0)` input;
the frozen table's observed maximum is five transitions. The production safety
guard remains 20.

## 9. Errors and out-of-contract inputs

The exactness claim applies only to the accepted grammar. Within it, operations
must not fail because of floating precision, tolerance, carry lookup, or value
rounding.

Behavior outside the grammar is compatibility-controlled rather than newly
specified. The candidate review must compare representative and exhaustively
enumerable baseline cases, including:

- empty and bare-radix strings;
- invalid digits;
- signs, whitespace, and exponent notation;
- repeated radix points; and
- non-`str` objects, including `bool`.

No deliberate exception-class or successful-result change outside the grammar
is permitted without a freeze amendment. A compatibility fallback is permitted
only under the conditions in the architecture freeze and must be unreachable
for accepted inputs.

## 10. Historical parity and correction ledger

The v0.17 baseline oracle governs byte parity as follows:

1. `add_cnrs` and `cnrs_add`: exact output parity for every accepted operand
   pair.
2. `cnrs_neg`: parity wherever the baseline output has the exact negated value;
   otherwise the result must change to the unique canonical exact value.
3. `cnrs_sub`: parity wherever the baseline output has the exact difference;
   otherwise the result must change to the unique canonical exact value.
4. `CVal`: exact output parity throughout the accepted domain.

The candidate evidence must list every fixed vector whose output changes and
must summarize exhaustive mismatch counts for the accepted test domain. A
changed result that is neither baseline parity nor independently exact is a
release blocker.

## 11. Independence and prohibited routes

For accepted inputs, production addition, negation, and subtraction must not:

- import `cnrs.validation`;
- use `complex`, `float`, tolerance comparison, `round`, `.real`, or `.imag`;
- call `cnrs_to_gaussian`, `gaussian_to_cnrs_digits`, or
  `gaussian_to_cnrs_str`;
- duplicate v0.15 normalization or v0.16 convolution;
- maintain a second addition transition relation; or
- trust a validation oracle or baseline fixture at runtime.

The validation oracle must not call the production operations it validates.

## 12. Non-goals

This contract does not alter or claim:

- `cnrs_eq` or general value-map exactness;
- multiplication, convolution, streaming division, or exact division;
- arbitrary infinite fractional-stream arithmetic;
- unrestricted analytic convergence or remainder control;
- full complex-value canonical representation; or
- Lean extraction or formal verification of the Python runtime.
